# GravityGate 需求澄清 Plan

## 0. 定位与风险前置

一个 Rust / Axum / Tokio 实现的独立反代网关，把 Google Antigravity（Cloud Code Assist）的模型能力包装成 OpenAI 兼容 API。

**必须先说清楚的风险**：四个参考项目无一例外声明，把 Antigravity 的 OAuth 凭据用于第三方代理**违反 Google ToS**，公开报告显示账号会被暂停、封禁或 shadow-ban。这不是能用工程手段消除的风险，只能压缩影响面。已知的具体打击面：

- `403 validation_required` —— 要求账号持有者完成人机验证才能继续
- `403 account_ineligible` —— 账号被标记为不符合资格
- ToS 封禁文案：`has been disabled` + `violation of terms of service`

工程上的应对是：账号池让单个账号被封不影响整体；每个账号的失败原因落盘可查（`verificationUrl`、`accountIneligibleReason`）；**不要用重要账号**。这一点会体现在 `/health` 和 Web 仪表盘的设计里，让用户随时能看到哪个账号进入了什么状态。

| 对客户端协议 | 无（宿主插件） | 无（宿主插件） | 仅 Anthropic | OpenAI Chat + Responses + Anthropic |

### 1.1 `antigravity-auth`（cortexkit）—— 上游真相的唯一来源

**特点**：这是唯一一个以**真实抓包**为基准的项目。`test-fixtures/agy-cli-1.1.24-*.json` 记录了 2026-09-02 从 agy CLI 1.1.24 抓到的完整请求头、信封字段顺序、以及每个模型的 `modelEnum` / `thinkingBudget` / `maxOutputTokens`。它还手写 HTTP/1.1 over TLS，而不是用 `fetch`。

**可借鉴（高价值）**：
- **wire identity**：`User-Agent: antigravity/cli/{ver} (aidev_client; os_type=...; arch=...; cl=974782877; auth_method=consumer)`，内容请求只带 `Authorization` + `Content-Type` + `Accept-Encoding: gzip`，**刻意不带** `X-Goog-Api-Client` / `Client-Metadata`（2.0 版本明确移除了，且要剥离 `x-goog-user-project` 否则 403）
- **信封字段顺序被强制**：外层 `project, requestId, request, model, userAgent, requestType`，内层 `contents, systemInstruction, tools, toolConfig, labels, generationConfig, sessionId`。抓包 fixture 把这些顺序都记下来了
- **项目上下文状态机**：`loadCodeAssist`(body `{metadata:{ideType:"ANTIGRAVITY"}}`) → `onboardUser`(poll 10×5s) → 缓存 30min（按 refresh token 哈希）→ 硬编码回退 `rising-fact-p41fc`。**绝不每次请求随机生成 project**
- **账号 schema**：字段设计极其完整 —— `rateLimitResetTimes`（按 claude / gemini-antigravity / gemini-cli 分键）、`coolingDownUntil` + `cooldownReason`、`verificationRequired` + `verificationUrl`、`accountIneligible`、`cachedQuota`、`capturedTierId`。而且有 V1→V4 的迁移链
- **限流分类器 + 退避阶梯**：`parseRateLimitReason` 把上游错误归成 5 类，`QUOTA_EXHAUSTED` 走 `[60s, 5m, 30m, 2h]` 阶梯
- **配额双池**：`retrieveUserQuotaSummary` 返回的 bucket 以 `gemini-*` / `3p-*` 前缀分池，对应 Gemini 和 Claude/GPT 两个独立配额池

**不可借鉴**：它是宿主插件而非独立服务，所以没有 HTTP 层、没有 admin 面、没有并发模型可抄。手写 HTTP/1.1 的做法在 Rust 里先不必照搬（见 M0）。

### 1.2 `opencode-antigravity-auth`（NoeFabris）—— 历史基线 + 反面教材

**特点**：最早、最简单的实现，单账号、无池、无配额轮询，UA 停在 `antigravity/1.11.5`。

**可借鉴**：几乎没有正面价值。唯一值得保留的是 `invalid_grant` 时清空凭据强制重登的处理。

**不可借鉴（且要引以为戒）**：它用 `generateSyntheticProjectId()` 每次请求生成随机项目 ID（`useful-fuze-ab12c` 这种）。`antigravity-auth` 的作者明确警告这**会破坏 prompt cache 并割裂服务端配额与会话状态**。这是本项目要主动避免的反模式。

### 1.3 `antigravity-claude-proxy` —— 翻译层质量最高

**特点**：Anthropic Messages 兼容，翻译层拆得很干净（`format/` 下 6 个单一职责模块）。**没有 OpenAI 路由**（我 grep 确认过全仓库不存在 `/v1/chat/completions`）。

**可借鉴（高价值）**：
- **7 阶段 schema 清洗流水线**：`$ref` → description 提示；`allOf` 合并；`anyOf`/`oneOf` 按评分扁平化（object 有 properties=3 分 > array=2 > 其他 type=1 > null=0）；`type:["string","null"]` 折叠；约束关键字（`pattern`/`format`/`minLength`）移进 description 文本；删除不受支持的关键字；类型名大写。这是从真实报错里磨出来的
- **签名缓存**：两张 TTL 表 —— `tool_use_id → signature`（因为 Claude Code 会在轮次之间丢掉非标准字段）和 `signature → family`（检测跨模型复用签名并丢弃）
- **工具循环恢复**：检测 `inToolLoop` / `interruptedTool` 状态，注入合成消息（`[Tool execution completed.]` + `[Continue]`）打破死锁
- **首事件缓冲**：在写响应头**之前**先拉第一个上游 SSE 事件，这样上游立即失败时能返回真实的 HTTP 4xx/5xx 而不是一个断掉的流
- **空响应重试**：上游返回空流 → `EmptyResponseError` → 退避重试 2 次 → 兜底合成文本，而不是返回一个静默截断的 200
- **测试范式**：`tests/helpers/http-client.cjs` 是一个能像 Claude Code 一样**重组 content block** 的 SSE 客户端（累积各 delta → `content_block_stop` → `JSON.parse(partial_json)`）。这是移植到 Rust 集成测试的黄金模板

**不可借鉴**：`count_tokens` 直接返回 501；`tool_choice` 被完全丢弃；`better-sqlite3` 读 Antigravity 本地库属于遗留路径。

### 1.4 `antigravity-gateway` —— 目标形态最接近，但 spec 是空的

**特点**：已经实现了三协议网关（OpenAI Chat Completions + OpenAI Responses + Anthropic Messages）。它的**核心架构决策是用 Anthropic Messages 作为内部 IR**，每个入口协议先转 Anthropic，再转 Google，出站反向转回。

**可借鉴（高价值）**：
- **OpenAI 适配层**：`openai-compat.js` 把 `thinking_delta` 映射到 `reasoning_content`（DeepSeek 风格），`reasoning_effort` 映射到 budget 20000/10000/5000；`openai-responses.js` 是完整的 Responses 事件状态机（`sequence_number` 计数器 + item index + `response.output_text.delta` 等全套事件）
- **会话亲和性**：`sessionId = SHA256(第一条 user 消息).hex[..32]`，稳定跨轮次 —— 这是让 prompt cache 真正命中的关键
- **乐观重置**：如果本地状态显示所有账号都限流，先 `resetAllRateLimits()` 强制重探一次，而不是盲目等待可能已经过期的本地状态
- **错误映射的取舍**：上游 429/配额错误**故意重新映射成 HTTP 400** `invalid_request_error`，因为 agentic 客户端会对 429/529 自动重试，配额耗尽时重试是纯浪费

**不可借鉴/需要注意**：它的 `openspec/` 目录是一个**未填写的模板**（`project.md` 里全是 `[Describe your project's purpose]` 占位符），没有任何真实 spec 可移植；`tests/` 全部是打真实上游的黑盒测试，**零 fixture、零 mock**；账号 schema 很薄（无 tier、无配额缓存、封号状态只有 `isInvalid` 一个布尔）。

### 1.5 四者共识的 wire 契约（这是最硬的产出）

```http
POST https://daily-cloudcode-pa.googleapis.com/v1internal:streamGenerateContent?alt=sse
Host: daily-cloudcode-pa.googleapis.com
User-Agent: antigravity/cli/1.1.24 (aidev_client; os_type=darwin; arch=arm64; cl=974782877; auth_method=consumer)
Transfer-Encoding: chunked
Authorization: Bearer <access_token>
Content-Type: application/json
Accept-Encoding: gzip
```

```
body = { project, requestId, request: {contents, systemInstruction, tools, toolConfig, labels, generationConfig, sessionId}, model, userAgent:"antigravity", requestType:"agent" }
```

上游 SSE 每行是 `data: {"response": {"candidates": [...], "usageMetadata": {...}}, "traceId": "..."}` —— 需要剥掉外层的 `response`。**没有 `event:` 名，没有 `[DONE]` 哨兵，终止条件就是连接关闭**。thinking 是 `{thought: true, text, thoughtSignature}` 形状的 part，Gemini 3 的 `thoughtSignature` 还可能挂在 `functionCall` part 上。限流错误体里带 `error.details[].{'@type':'type.googleapis.com/google.rpc.RetryInfo', retryDelay:'3.957525076s'}`。

## 2. 已确认的需求决策

| 决策项 | 结论 |
|---|---|
| 客户端协议 | 第一阶段只做 **OpenAI Chat Completions**（`/v1/chat/completions` + `/v1/models`）；第二阶段加 **OpenAI Responses**；**不做** Anthropic / Claude 协议适配 |
| 上游 Claude 模型 | **支持**。`claude-opus-4-6-thinking` / `claude-sonnet-4-6` 作为可路由模型暴露，保留 Claude 专用变换分支 |
| 内部 IR | **Google GenAI 形状为规范 IR**（`contents`/`parts`，thinking 是原生 part） |
| 凭据录入 | 浏览器 OAuth PKCE + 手动粘贴 refresh token。不做 SQLite 导入，不做手动 API Key |
| 凭据存储 | **明文 JSON（0600）**，与四个参考项目一致 |
| 路由默认 | **hybrid 打分**（token bucket + health score + LRU），可配置 |
| 可观测性 | 状态 JSON 接口 + Prometheus 指标 + Web 仪表盘 + SQLite 请求审计（**四项全要**） |
| thinking tier | **基名 + tier 后缀双支持**，并读 `reasoning_effort` |

注意「不做 Claude 协议适配」与「支持 Claude 模型」是两件事：前者指不实现 `/v1/messages` 入站协议，后者指 Claude 模型仍然可以从 OpenAI 协议调用——它们是上游最强的两个模型，且它们走的仍是 Google 形状的 wire，只是需要一条 Claude 专用的 `generationConfig` 变换分支。

### 3.2 关键依赖与实现约束

- `axum` + `tokio` + `tower-http`（trace/cors/compression）
- `reqwest`（rustls-tls + gzip + brotli + stream），**或**在 M0 验证失败时降级到 `hyper` + `rustls` 手写请求头
- **`serde_json` 必须开启 `preserve_order` 特性** —— 信封字段顺序有强制要求，默认的 `BTreeMap` 会按字母序重排导致顺序错乱。这是本项目最容易被忽略的实现约束
- `tokio-util`（codec）、`futures` / `async-stream`（流组合）
- `moka` 或手写 `Mutex<HashMap>` + 惰性过期做签名缓存
- `metrics` + `metrics-exporter-prometheus`
- `rusqlite`（bundled）做审计日志
- `rust-embed` 或 `include_dir` 嵌入仪表盘静态资源
- `clap` / `toml` / `thiserror` / `tracing` / `sha2` / `base64` / `rand` / `uuid`

### 3.3 三个必须做对的子系统

**A. Thinking 签名保真（最容易出错的部分）**

上游 thinking part 是 `{thought: true, text, thoughtSignature}`，Gemini 3 的 `thoughtSignature` 还可能挂在 `functionCall` part 上，长度 <50 的签名视为无效。

关键问题是：**OpenAI 协议里根本没有签名字段**。上游要求多轮对话回传签名，但 OpenAI 的 `tool_calls` 结构无处安放它，客户端也不会保留非标准字段。所以签名必须**完全由网关缓存维护**，键是 `tool_call_id`——这是本项目与参考项目最本质的差异，参考项目走 Anthropic 协议，签名有 `signature_delta` 和 `thinking.signature` 可以承载，而我们走 OpenAI 协议没有这个载体。

设计：
- 两级 TTL 缓存：`tool_call_id → signature` 和 `signature → family`（claude / gemini）
- 发回上游时按目标模型的 family 过滤签名：Gemini 目标丢弃非 gemini family 的签名
- 缺失签名时给 `functionCall` part 注入哨兵 `skip_thought_signature_validator`
- 助手内容重排序为 thinking → text → tool_call
- 工具循环恢复：检测中断的循环并注入合成消息

**B. 重试状态机（账号 × endpoint 两层嵌套）**

参考项目里这是个用 `attempt--` 和 `continue`-不递增的 hack 拼出来的双层循环，在 Rust 里应该显式建模成状态机：

```rust
enum Step { TryEndpoint, RetrySameEndpoint(Duration), RotateAccount, WaitAllLimited(Duration), GiveUp(Error) }
```

每层的行为：
- **endpoint 层**：429 先试下一个 endpoint，取各 endpoint 的最小 reset 值；5xx 睡 1s 再试下一 endpoint；401 清该账号 token+project 缓存后重试
- **账号层**：endpoint 全失败后标记限流并换账号；连续 3 次 5xx/网络失败 → 60s 冷却
- **池耗尽**：等待时间 ≤ 阈值（默认 120s）则 sleep 后重试，否则返回错误
- 乐观重置：本地状态显示全限流时，先清一次状态强制重探

**C. 首事件缓冲 + 错误语义**

流式接口在写响应头之前先拉第一个上游事件。这样上游立即报错（401/403/配额）时返回的是真实的 HTTP 状态码 + JSON 错误体，而不是一个 200 后面跟着断掉的 SSE 流。

错误映射策略（**这里我要偏离参考项目的做法，理由如下**）：参考项目把配额耗尽映射成 400，理由是 Claude Code 会对 429 自动重试。但 OpenAI 生态客户端的语义是——429 是「稍后重试」且会读 `Retry-After`，400 是「请求有问题，别重试」。我们希望上游耗尽的配额是少数账号的局部状态，网关应该内部消化（换账号），只有在**整个池都耗尽且等待时间超过阈值**时才暴露给客户端。所以：

- 池内可恢复的限流 → 网关内部换账号/等待，客户端无感
- 池整体耗尽 → **429 + `Retry-After` + 人类可读的重置时间**（默认）
- 提供 `exhausted_error_mode = "429" | "400"` 配置项，想要参考项目的行为可切换

### 3.4 路由与账号状态

hybrid 打分（照搬 `antigravity-auth` 的常数，已被实践检验）：

- token bucket：上限 50，每分钟回填 6，失败退还
- health score：初始 70，成功 +1，限流 −10，失败 −20，每小时休息恢复 +2，可用阈值 50，上限 100
- 综合分 = `health×2 + (tokens/max)×100×5 + min(空闲秒, 3600)×0.1`
- 粘性加成 150、切换阈值 100（防止分数抖动导致频繁切账号破坏 prompt cache）
- 按 family 分别记录 activeIndex（claude / gemini 两条独立游标）
- 配额软阈值：剩余低于阈值（默认 20%）主动轮换
- 乐观重置：全限流时先清状态再重探

账号 schema 覆盖 `rateLimitResetTimes`（按 claude / gemini 分键）、`coolingDownUntil` + `cooldownReason`、`verificationRequired` + `verificationUrl`、`accountIneligible`、`cachedQuota`、`capturedTierId`。

### 3.5 模型暴露方案

`/v1/models` 由「静态元数据表 + 上游 `fetchAvailableModels` 实时拉取」合并而成，缓存 5 分钟，拉取失败时 fail-open 退回静态表。

公开模型 ID 直接用上游 wire 名（`gemini-3.8-flash`、`claude-opus-4-6-thinking`），不额外加命名空间前缀——保持客户端配置最简单。解析优先级：

```
模型名 tier 后缀 (gemini-3.8-flash-high)  >  thinking.budget_tokens  >  reasoning_effort  >  默认 medium
```

已知的当前模型集（来自 1.1.24 抓包，`/v1/models` 会以实时拉取为准）：

| 模型 | context / output | 配额池 |
|---|---|---|

## 4. 里程碑拆分

**M0 —— 可行性验证（spike，先做这个）**
最大的技术不确定性是：`reqwest`/`hyper` 发出的请求能否被上游接受？`antigravity-auth` 特意手写了 HTTP/1.1，理由是后端对 header 顺序和连接行为敏感，而 Rust 的 `http::HeaderMap` **不保证插入顺序**。手工构造一个最小请求打真实上游验证；失败时的退路是用 `hyper` + `rustls` 接管连接并手写请求行/头部块。产出：`examples/spike.rs` + 结论记录。

**M1 —— 上游连通骨架**
config、tracing、transport、envelope、常量、UA；手动 refresh token 录入与刷新；项目上下文发现。验收：用固定账号完成一次非流式 `generateContent` 并打印结果。

**M2 —— 账号池 + 路由**
Account schema、原子存储 + 文件锁、三套 tracker、hybrid 选择、限流分类 + 退避、封号检测；`/health` + `/account-limits`。验收：多账号轮换、限流自动切换、账号状态可查。

**M3 —— Streaming + IR 翻译**
上游 SSE 解析、Google IR、OpenAI chunk 输出；thinking → `reasoning_content`；签名缓存；tool call 全链路 + schema 清洗。验收：端到端流式对话、thinking、tool call 三者都通；用「重组 content block」式的集成测试覆盖。

**M4 —— OAuth**
PKCE、51121 回调服务、无头降级（手动粘回调 URL）、userinfo 取 email。验收：`gravitygate account add` 走完浏览器授权。

**M5 —— 非流式 + 收尾**
非流式路径、统一错误映射、`/v1/models` 实时拉取、`/refresh-token`、Docker 镜像。

**M6 —— 可观测性**
Prometheus `/metrics`、SQLite 审计日志、Web 仪表盘（账号列表 + 配额进度条 + 限流倒计时 + OAuth 跳转）。

**M7（第二阶段）—— OpenAI Responses**
`/v1/responses` + 事件状态机（`sequence_number`、item index、全套 `response.*` 事件）。

M0–M3 是核心闭环，建议先做到 M3 再评估后续节奏。M6 的四项可观测性里 Web 仪表盘工作量最大，但它依赖的账号/配额数据在 M2 就已就绪，可以并行推进。

## 5. 我做了默认假设的开放项

以下我没有再打断你确认，先给出默认决策和理由，如果与你的预期不符请直接指出：

1. **客户端鉴权**：网关侧支持可选的静态 API key 列表（`Authorization: Bearer` 或 `x-api-key`），留空则不校验。四份参考项目都这么做，本地部署场景下最省事
2. **thinking 输出字段**：默认发 `reasoning_content`（DeepSeek 风格，Cline / Roo / OpenRouter 系客户端普遍识别），提供配置项可额外双写 `reasoning` 字段
3. **`tool_choice` 映射**：参考项目直接丢弃了它，我们做完整映射 —— `none`→`NONE`、`auto`→`AUTO`、`required`→`ANY`、指定函数→`ANY` + `allowedFunctionNames`。成本很低而收益明确
4. **配置目录**：`$GRAVITYGATE_CONFIG_DIR` → `$XDG_CONFIG_HOME/gravitygate` → `~/.config/gravitygate`（Windows 走 `%APPDATA%\gravitygate`），账号文件 `accounts.json` 权限 0600、目录 0700
5. **默认端口 8080**，配置格式 TOML + `GG_*` 环境变量覆盖
6. **Web 仪表盘技术选型**：无构建步骤的原生 HTML/CSS/JS 内嵌（避免引入 Node 构建链），仅调用同源的 JSON 接口
7. **审计日志 schema**：`(id, ts, account_email, requested_model, wire_model, stream, prompt_tokens, completion_tokens, cached_tokens, latency_ms, status, error_code, retry_count)`
