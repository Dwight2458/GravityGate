# 路由恢复与运行状态一致性方案

日期：2026-10-15。状态：待实施。本次仅提交方案，不修改运行逻辑、不重启服务。

## 目标与现场依据

现有代码把 `health < 50` 作为禁止选择条件，而健康分数自然恢复只有每小时
2 分。账号从 100 降到 40 后，即使 60 秒冷却结束，也可能再停用约 5 小时。
账号列表和 `/health` 主要查看保存状态，错误描述又不包含运行时健康筛选，
因此出现“一个账号 ready，服务持续 503，错误只提另一个账号需要验证”。

2026-10-14 现场对比：旧服务返回 503；相同账号通过新 CLI 进程 probe 返回
200 / ok。模拟复现也确认：保存状态可用、冷却已结束、健康分数 40 的账号，
当前路由仍返回 NoCandidate。尚未取得导致现场首次扣分的原始上游错误。

验收目标：临时故障可以在有限时间后恢复尝试；真实验证与额度限制仍有效；
并发请求不会集中探测；运维界面能够说明每个账号、端点与模型的实际阻塞原因。

## 1. 健康分数与准入分开

- 删除四种路由策略中以健康分数硬性排除账号的逻辑。健康分数仅用于择优。
- 是否可以请求由明确的 gate 决定：禁用、凭据失效、验证、额度、令牌桶、熔断。
- 网络和服务端故障不再写账号级通用冷却，与对应作用域的熔断统一管理，避免两套
  冷却互相阻塞。旧版保存的未到期冷却记录仍予以尊重，到期后允许重新参与路由。
- 一次成功可以关闭匹配作用域的熔断、清除该作用域连续失败次数。恢复不再依赖
  健康分数每小时增加到门槛；其他模型的成功也不能错误清除失败模型的额度记录。

## 2. 按失败作用域处理

| 结果 | 作用域 | 路由行为 |
|---|---|---|
| 验证、封禁、失效凭据 | 账号/凭据 | 保留对应账号的 hold，其他账号继续服务 |
| 明确额度耗尽、短期速率限制 | 账号 + 模型组 | 使用现有持久化额度记录，优先采用上游重试时间 |
| 无具体原因的 429 | 账号 + 模型组 + 端点 | 保守短冷却，保留 Unknown，不推断为整族额度耗尽 |
| 连接、DNS、TLS 等传输失败 | 上游端点 | 端点暂退并尝试备用端点，不逐个扣完所有账号 |
| 上游 HTTP 5xx | 上游端点 | 有限重试，达到阈值后端点熔断 |
| 模型容量不足 | 端点 + 模型组 | 对该模型退避，不影响其他模型的账号资格 |
| 无效请求、未知模型明确 404 | 当前请求 | 终止请求，不冷却账号 |
| 客户端取消 | 当前请求 | 释放占用，不作为上游故障计数 |

OAuth invalid_grant 或确认失效的凭据只停用该凭据并轮换；修正现有
AuthInvalid 直接终止所有账号尝试的行为。保留先前修复的未知模型 404 终止策略。
Flash 各档位及已确认的 tiered 名称继续共享模型组，Pro、Claude 独立判断。

## 3. 有期限的熔断与单请求恢复尝试

每个临时故障作用域使用三种状态：

```text
Closed（可用） --连续故障达到阈值--> Open（暂退）
Open --到达 next_retry_at 且有真实请求--> HalfOpen（一个恢复尝试）
HalfOpen --匹配作用域已恢复--> Closed
HalfOpen --再次故障--> Open（更长退避）
```

建议初始参数：连续失败阈值 3，首次熔断 60 秒，后续按 2 倍增长，最大 300 秒，
加入约 ±20% 随机抖动。每个作用域只允许一个 HalfOpen 在途尝试。这些是本项目
的建议默认值，实施时通过配置校验与测试固定，不是 Google 的额度参数。

- 计数按逻辑请求归并：同一请求在同一作用域内的多个内部重试至多累计一次失败，
  HalfOpen 的失败则立即重新熔断。一个端点成功不能清除另一个端点的失败历史。
- 到期只表示允许试探，不能直接宣称恢复。优先保留健康备选；没有健康备选时，
  允许一个到期候选承担真实请求，不再因为历史低分永久拒绝所有候选。
- 默认由真实流量触发恢复，不额外启动循环生成探针；没有流量时无需消耗额度。
- 选择候选、占用 HalfOpen 租约和扣除本地令牌必须在同一个同步边界内完成，
  解决当前 select 与 consume_token 分离的竞争。
- 用 RAII 租约保证成功、失败、超时、取消、提前返回时都释放占用。租约带代次，
  旧请求的迟到结果不能覆盖新一轮 Open 状态。
- 恢复尝试的超时绑定实际请求预算；若增加独立上限，建议默认 180 秒并允许配置。
  超时必须先取消底层上游，再释放租约，不能仅因租约时钟到期就放行第二个探针。
- 结果按作用域解释：有效 HTTP 响应可以证明连接恢复；429 可能解除传输故障，
  同时建立额度 gate。模型生成恢复需检查有效输出，不能只因收到 200 响应头就
  清除空流或读取异常历史。已向客户端输出内容的流失败后，不透明重放整次生成。

## 4. 统一状态计算与等待语义

新增只读 RoutingSnapshot，至少包含：模型组、账号保存状态、健康分数、令牌余额、
各作用域熔断状态、所有阻塞原因、最早恢复尝试时间、最后失败类别及发生时间。
路由准入、`/health`、管理接口和错误描述复用同一套评估规则；实际抢占租约在
选择时重新校验。查询状态本身不得抢租约、消费令牌或调用上游。

- `/health?model=gemini-3.8-flash-high` 展示该模型的有效路由状态。未指定模型时
  明示为账号总体状态，不把“保存状态允许”描述成任意模型都能服务。
- `gravitygate account list` 明示展示的是保存状态；增加计划中的 `--live --model`
  查询运行服务状态。服务不可达时明确报告不可达，不静默回退后仍声称 live ready。
- 返回完整原因，例如：账号 A 等待验证；账号 B 可用但 daily 端点熔断，38 秒后
  可重试；备用端点也不可用。不会再仅因为 A 需要验证，就漏掉 B 的阻塞原因。
- 单账号存在多个临时 gate 时，等待时间取这些 gate 的最大值；在可恢复账号之间
  取最小值。已禁用或验证尚未到重试窗口的账号不贡献虚假的短恢复时间。
- 令牌桶等待、真实额度限制、端点故障、HalfOpen 被占用分别记录，不再都写成
  every account is rate limited。被其他请求占用的 HalfOpen 通过通知/有界等待
  处理，禁止零间隔轮询。
- 临时令牌/额度限制使用 429；暂时无可用端点或恢复请求在途使用 503；可确定
  恢复时间时附带正确向上取整的 Retry-After。HTTP 响应保留 OpenAI 错误结构。
- 若所有候选都需要人工处理且没有自动恢复窗口，明确返回非重试类的 403 与
  `account_action_required`，而非笼统的 retryable 503；仍存在验证重查窗口时，
  用 503 与该窗口的 Retry-After 区分。单个账号需人工处理不能盖过其他账号的
  可恢复状态。网关访问密钥失效仍单独使用 401，不混同上游账号故障。
- 队列、额度等待、熔断等待、重试共同受请求级等待预算约束；客户端取消会终止
  后续等待和尝试，不能在每层循环重新获得完整预算。

## 5. 保存足够的故障证据

保留现有请求汇总，并给它添加 request_id。新增逐次 attempt 记录表，采用兼容的
SQLite 迁移，不丢弃旧审计数据。旧记录没有的数据保持未知，不伪造为零次尝试。

每次实际尝试记录：request_id、attempt_id、凭据短 ID、模型组、端点、阶段
（凭据准备/发送/读流）、耗时、HTTP 状态、分类原因、上游重试提示、采用的退避
及来源、路由决定。最终失败仍保留真实尝试次数和已尝试账号。

INFO/WARN 至少记录失败分类与熔断状态变更，排查不再依赖预先开启 debug。
完整错误体仅作受限诊断，裁剪并过滤凭据等敏感字段。审计写入失败不阻塞服务。
指标使用有界标签区分 token_bucket、quota、endpoint、capacity、verification 等
原因，不把请求 ID 或任意模型名作为时序标签。

## 6. 手动恢复入口

增加计划中的运行时 routing reset 管理操作，用于账号或指定作用域的临时路由
状态复位：清理临时熔断/历史分数，进入一次受控恢复尝试，而非无限放行。
它不能清除禁用、验证、封禁或真实额度限制，也不清空对话、签名和会话缓存。
保留管理鉴权并记录操作事件。

现有 `/refresh-token` 保持凭据/缓存操作语义，不把它当作路由重置按钮。
运行时重置仅为应急手段，自动恢复应在不调用它、不重启进程时通过验收。

第一阶段应同时具备基础快照和状态变更日志，保证恢复行为可观察后再接真实流量。

仓库中已有的限流修复保持不变，新实现叠加在当前工作区上。

## 8. 必须通过的验收用例

1. 账号 A 待验证，B 分数 40 但没有活动 gate：B 可被选择并成功，不能因分数低卡死。
2. 账号或端点熔断 60 秒后，一个真实请求进入 HalfOpen；成功恢复，无需重启服务。
3. 100 个并发恢复请求，在同一作用域最多一个探测；令牌余额不因选择竞争透支。
4. HalfOpen 超时、取消、任务提前退出后可以恢复调度；旧代次成功不能误关新熔断。
5. 上游持续失败时退避有上限但不形成请求风暴；客户端取消后不继续后台重试。
6. 真实验证、禁用、失效凭据、额度限制仍然生效，其他账号或模型仍可工作。
7. primary 端点故障时可用 fallback 接管；模型容量故障不波及其他模型。
8. 未知模型 404、真实 429、混合 gate、所有账号需人工处理均返回准确状态和原因。
9. 200 空流或读流失败不误报模型恢复；已输出的流不被透明重放。
10. CLI live 状态、`/health?model=`、路由结果和错误详情在同一快照下相符。
11. 多次尝试后失败也能从 request_id 找到每次 HTTP/传输故障；旧审计库迁移成功。
12. 使用虚拟时钟与本地 HTTP 服务复现连续故障和恢复，再运行完整测试与 Clippy。

上线小流量验证重点是“一个账号待验证、另一个账号遭遇短暂故障后自动恢复”。
不通过向 Google 连续制造错误或长时间生成探针来测试恢复机制。
